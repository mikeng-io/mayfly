Ephemeral GitHub Actions runners on Lambda MicroVMs — proven

Feasibility validated end-to-end on real MicroVMs (Tokyo). Each CI job runs in a fresh, single-use MicroVM — JIT-registered, one job, dies. The two things that could have killed it (does it stay alive through a job; can it build containers) both work.

What was verified

✓

JIT hand-off over the L7 endpoint

A MicroVM exposes only a token-auth HTTPS endpoint (no raw socket). An in-VM launcher receives the JIT config over it and starts the runner.

endpoint health 200 · jit 202 · runner connected
✓

A MicroVM holds a runner through a job (the make-or-break)

Auto-suspend follows inbound traffic; the runner is outbound-only. With auto-suspend off, the MicroVM stays up for the whole job.

microvm=RUNNING t=10→140s · 120s job · completed/success
✓

Docker build/run inside the MicroVM

dockerd runs in the VM (own kernel, ALL caps) — containers-in-a-VM, not nested virt. First try.

docker version linux/arm64 · Hello from Docker! · Successfully tagged
✓

Real ARM64 npm build — no friction

Astro (Vite/esbuild/Rollup native deps): setup-node → npm install → astro build. Lockfile isn't x86-locked; npm installs arm64 variants.

added 329 packages · astro build · ASTRO_BUILD_OK arch=aarch64

Constraints & field notes

Honest constraints

  • arm64ARM64 (Graviton) only. Native ARM builds; x86 = QEMU emulation (opt-in setup-qemu+buildx, slower, binfmt-in-VM unverified).
  • L7L7-only ingress (no raw L4 / stable IP). Fine for a runner (outbound to GitHub); killed the earlier "regional proxy" idea.
  • idleAuto-suspend is inbound-driven; run job-carrying VMs with it off, suspend explicitly between jobs.
  • imageImage "fatness" is a choice — lean + setup-* actions (verified) vs a fat GitHub-like image.

MicroVM gotchas (article gold)

  • cliaws-cli 2.1.2 didn't know the 2-week-old service → upgrade to ~2.28+.
  • 403The --hooks shorthand → a bogus 403 "Unable to determine service/operation". Omit it.
  • enumFailure state is CREATION_FAILED, not CREATE_FAILED; 3 independent states (image/version/activation).
  • arnget/run image ops need the ARN, not the name; microvm ops take the ID.
  • regionAccount default region ≠ MicroVM region — pin it (Singapore has none).

Positioning & cost

Why not CodeBuild? It already hosts GHA runners in-VPC (managed, mature) — for production, use it. Mayfly's real edge: microVM own-kernel isolation for untrusted code + warm-start at ~zero idle cost via suspend/resume (CodeBuild forces reserved-pay-for-idle or on-demand-cold). Narrow but real.

Cost: the whole validation ran for a few cents — a handful of short MicroVM runs, all auto-terminated. Standing footprint ≈ $0. Every resource is CDK-managed or ledgered with a teardown step.
