Direct vs. SNI-proxied: how the connection really flows

Same request — chat.openai.com from Hong Kong — two ways. The proxy changes exactly one thing that matters: the IP the server sees. It does that by staying in the path and forwarding encrypted bytes it cannot read.

Client · Hong Kong SNI proxy · Tokyo Server · chat.openai.com

1 · Handshake

Direct

non-proxied
Client·HK──▶Server
  1. TCP connect straight to the server's real IP (DNS gave you the real answer).
  2. Send ClientHello — SNI: chat.openai.com.
  3. Server replies ServerHello + certificate.
  4. TLS established directly, client ↔ server.
resultOne TCP connection. The server already sees your HK IP.

Via SNI proxy

Control D model
Client·HK──▶Proxy·Tokyo──▶Server
  1. TCP connect to the proxy's IP (DNS handed you the proxy, not the real host).
  2. Send ClientHello — SNI: chat.openai.com.
  3. Proxy reads the SNI (it's plaintext), opens its own TCP leg to the real server.
  4. Handshake is relayed end-to-end — proxy pipes bytes, never decrypts.
resultTwo TCP legs stitched together. TLS is still client ↔ server; the proxy is blind.

2 · Data transfer

Direct

non-proxied
Client·HK◀──▶Server
  1. Encrypted application bytes flow straight between client and server.
  2. Nothing sits in between.
resultEvery packet arrives from your HK IP.

Via SNI proxy

Control D model
Client·HK◀──▶Proxy·Tokyo◀──▶Server
  1. Every byte flows through the proxy, both directions, for the whole connection.
  2. It's a blind pipe — the proxy copies ciphertext it can't read.
resultThe server sees the proxy's Tokyo IP — your IP is masked.

3 · HTTP request

Direct

non-proxied
Client·HK──▶Server
  1. GET /v1/… travels inside the TLS tunnel, straight to the server.
  2. The server decrypts and handles it.
resultRequest arrives from HK → the geo rule is applied to you.

Via SNI proxy

Control D model
Client·HK──▶Proxy·Tokyo──▶Server
  1. The HTTP request is inside TLS — the proxy cannot read it, only forwards it.
  2. The server decrypts it at the far end.
resultRequest arrives from Tokyo → the geo rule is applied to Tokyo.

What the proxy can see

✓SNI hostname — chat.openai.com, sent in plaintext in the ClientHello. This is all it needs to route.
✗The HTTP request / response — encrypted end-to-end; the proxy never has the key.
✗Your data — passwords, tokens, payloads. Ciphertext to the proxy.

What the server sees

✗Direct: your real Hong Kong IP — geo-block applies.
✓Proxied: the proxy's Tokyo IP — geo-block sees Tokyo, not you.
·In both cases it still terminates real TLS with the client — the proxy is not a man-in-the-middle.
The proxy doesn't decrypt, doesn't understand HTTP, and doesn't change your request. It reads one plaintext field (the SNI) to decide where to forward, then stays in the path copying encrypted bytes. DNS only decides whether you go direct or through the proxy — the proxy does the actual work, and it's the reason the server sees Tokyo instead of Hong Kong.
