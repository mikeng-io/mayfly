Mayfly, and why not CodePipeline / CodeBuild

The honest version: CodeBuild already hosts GitHub Actions runners in your VPC. So Mayfly has to earn its place — and the comparison shows exactly the one thing it does that CodeBuild's model structurally can't.

Current architecture

GitHubworkflow_job: queued — a job with runs-on: [self-hosted, mayfly] fires a webhook.
↓
Webhook · LambdaVerify HMAC → filter queued + mayfly label → return 2xx fast → enqueue.
↓
Queue · SQSShort delay — decouples the ack, lets fast cancellations settle.
↓
Control · LambdaRe-check still queued → fork check → resume a suspended MicroVM → mint & inject a JIT config (name = job id).
↓
Runner · MicroVMIn your VPC. Runs run.sh --jitconfig for one job; reaches private resources (RDS) under its security group. Fork PRs get none.
↓
TeardownThree layers: VM self-terminates on process exit · completed webhook · reconciler sweep. A replacement is warmed to hold the pool.

State + correlation {jobId → microvmId → runnerName} in DynamoDB · auth via a GitHub App (1-hour install tokens).

Why not CodePipeline?

CodePipeline is orchestration (source → build → deploy), not a runner. Using it would mean migrating your CI off GitHub Actions — abandoning your existing workflows, the marketplace-action ecosystem, and developer familiarity.

Mayfly's goal is the opposite: keep your GitHub Actions workflows exactly as they are, and only change where the compute runs. So CodePipeline isn't the comparison — CodeBuild is.

Why not CodeBuild-hosted GitHub Actions runners?

This is the real question. CodeBuild runs your GitHub Actions jobs on AWS, in your VPC, ephemerally — since 2024. It gives you two fleet modes, and forces a trade between them:

The bottom two rows are the whole point. CodeBuild makes you choose: reserved capacity (fast, but you pay for idle hosts) or on-demand (no idle cost, but cold starts). Mayfly is the only column with both — fast start and ~zero idle cost — because a MicroVM can suspend to zero and resume in milliseconds. That combination is the novel capability, and it's what the article is actually about.

The honest verdict

Use CodeBuild if…

  • You want production CI on AWS today — managed, mature, supported.
  • Native AWS integration (IAM roles, Secrets Manager, CloudTrail) is built in — Mayfly would have to add it.
  • You don't want to run a control plane.
  • Reserved-capacity idle cost, or on-demand cold starts, are acceptable.

Mayfly's reason to exist

  • It showcases the two-week-old Lambda MicroVM primitive in a real scenario.
  • It delivers the one thing CodeBuild's model can't: warm start at ~zero idle cost, via suspend/resume.
  • A self-owned control plane — a building block SREs can shape (pooling, policy, lifecycle), not a black box.

For the write-up: address "why not CodeBuild" head-on. It's the first thing a reader asks — and the honest answer (CodeBuild wins for production; Mayfly explores a capability it lacks) is what makes the piece credible.
