The in-VM launcher hand-off works

Question: can an in-VM launcher receive a JIT runner config over an HTTP endpoint (the way it must, since a Lambda MicroVM exposes only an L7 endpoint — no SSH, no raw socket) and run one real GitHub Actions job to clean exit?

real repo: mikeng-io/mayfly-test runner v2.335.1 · arm64 Docker stands in for the MicroVM no AWS · 2026-07-08

What it did — the exact sequence

1Control plane mints a JIT config — POST generate-jitconfig → GitHub returns encoded_jit_config. Administration:write
2Hands the config to the in-VM launcher over HTTP → 202 Accepted. models the MicroVM L7 endpoint
3Launcher runs run.sh --jitconfig <blob> → runner connects to GitHub outbound (no inbound needed).
4Workflow dispatched → job smoke queued → GitHub assigns it to the online runner.
5Runner executes the job → Succeeded.
6Ephemeral: runner removes its credentials, exits 0 → launcher exits 0 → container stops. Runner auto-deregisters.

What it proves — and what's still open

✓ Proven / de-risked

  • ✓JIT config → run.sh --jitconfig works with a fine-grained PAT — one atomic call, nothing leakable on the box.
  • ✓The in-VM launcher HTTP hand-off is the concrete answer to "how do you inject the config given L7-only ingress."
  • ✓Runner is outbound-only — it dials GitHub; no inbound rule, no public listener.
  • ✓Ephemeral single-job lifecycle behaves — runs one job, auto-deregisters, exits clean.

◑ Not yet proven → Phase 2

  • ?Does a real Lambda MicroVM stay running (not auto-suspend) while the runner long-polls and executes? The make-or-break.
  • ?The real L7 endpoint + X-aws-proxy-auth bearer hand-off (here modeled with a plain container port).
  • ?run / suspend / resume / terminate behavior with a live runner inside.
Honest caveat: local Firecracker isn't available on macOS, so a Docker container stood in for the MicroVM. That proves the GitHub + launcher logic — not the Lambda MicroVM platform behavior, which is exactly what Phase 2 (real AWS) exists to test.
